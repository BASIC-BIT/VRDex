# Capacity Unit Test Seam Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task, following the user-selected method. Use a fresh implementer and fresh reviewer for each task; Root alone owns operational actions. Steps use checkbox (`- [ ]`) syntax for tracking. The planning author does not spawn agents.

**Goal:** Restore meaningful isolated backend and bridge tests with explicit synthetic capacity while every default production admission path remains closed.

**Architecture:** Type the existing resolver, close over it in a scheduling registration factory, and override only that registered mutation through each Convex test fixture's module loader. Thread the same dependency through the existing bridge task-definition seam and its loop options. Retain default rejection and same-process isolation coverage.

**Tech Stack:** Node 24 node:test, TypeScript/tsx, JSDoc ES modules, Convex 1.32.0 and convex-test.

**Spec:** [Capacity unit test seam design](../specs/2026-10-26-capacity-unit-test-seam-design.md); required review: [Capacity unit test seam design review](../../engineering/authority/reviews/capacity-unit-test-seam-design-review.md).

## Global Constraints

- Keep the production measured map empty and keep the real default registrations. Never make fixture evidence IDs, database rows, RPC arguments, or environment data authorize capacity.
- Use the same resolver for fresh allocation and `validateMeasuredSnapshot(validateAllocationSnapshot(...), resolver)`, including scheduled existing-session paths. Neither snapshot validator may be removed or bypassed.
- Keep authorization, account authority, event time, output destination, open/claimed session, immutable media settings, frozen simulcast membership, profile, allocation shape, evidence, and resource-limit assertions. Existing negative tests should continue to assert their intended errors under the synthetic resolver.
- Keep ordinary factory export in events.ts; underscore filenames do not exclude code from deployment. Verify analyzed function names, not just generated-file contents.
- Keep synthetic allocation exactly `{cpuUnits:4096,memoryMiB:8192,evidenceId:"fixture-capacity-v1"}` for six presets x both simulcast states. This is test data, never measured production evidence.
- The actual-admission migration contract, tests, historical fixture and receipt semantics remain unchanged. Positive whole-flow production admission remains blocked on measurements and its original CI gate remains red. No synthetic admitted migration fixture is added.
- No new packages, environment authority, public arguments, module mocking, mutable resolver setters, generic fixture framework, casts or `any`. Retain the narrow existing control-only direct seed fixture.
- This plan covers unit seams, synthetic fixtures, production rejection, typing and local function analysis only. It does not establish merge readiness or authorize source edits during planning.

## Review Focus

- A production fixture created alongside a synthetic fixture must continue rejecting after synthetic admission succeeds; Task 1 isolation test covers shared-state leaks.
- Reusing a persisted synthetic snapshot must reject without mutating existing session/program/command/audit rows; Task 1 before/after test covers this.
- A valid snapshot with changed allocation evidence or destination profile must still fail the two real validators; Task 1 validator-preservation test covers this.
- Default bridge rejection happens after admission; Task 2 asserts release/error reporting and absence of registration, launch marker and RunTask.
- A mistakenly changed shared fixture must fail literal 4096/8192 assertions; Task 2 capacity and Lambda tests cover it independently of resolver equality.
